# AI layer: brainstorm notes

**Status:** brainstorm in progress, 21 November 2026. **Nothing here is approved.**
These are notes to pick up from, not a spec. Recommendations are marked as the
builder's leaning; only the points marked *(owner)* came from the owner.

## 1. What is being planned

Ahead of time, the owner wants to add:

- **Agents**, with **retrieval, scoring and evals**
- **Semantic recall** (search by meaning)
- **Two chatbots:**
  - **Shop assistant:** helps a customer find products and build a basket, then place the order
  - **Admin assistant:** answers analytics questions for the shop's side

Two decisions were raised: **which framework**, and **what owns what** (the Python
backend, or the Next.js frontend).

## 2. What in the project shapes this

1. **Business rules live in Python** (AGENTS.md). A bot that builds baskets must not
   compute prices, totals, VAT or stock. Its tools call the same domain code as
   `POST /cart/quote`, so the tools are Python whatever the framework.
2. **The cart lives in the browser's localStorage** (storefront spec §5). A bot on
   the server can't write to it. The bot proposes cart changes, the browser
   applies them, and every number still comes from the cart quote.
3. **The two bots see different data.** The admin bot needs `unit_cost` for margins;
   the public API must never expose it. There is no sign-in or admin area yet.
   Local-only lowers the stakes, but the boundary still has to be real.
4. **Single source of truth.** "No second store" puts embeddings in PostgreSQL
   (pgvector), not a hosted vector database. Analytics is already planned as DuckDB
   and pandas (Python). Evals fit the existing pytest culture: invariants, mutation
   checks, the deterministic seed (42).

Search is a v1 non-goal in the storefront spec, so semantic recall would be the
shop's first search.

## 3. Frameworks considered

Versions checked 21 November 2026; all are actively maintained.

| Option | Version | Strength | Fit for CommerceLab |
|---|---|---|---|
| **LangChain / LangGraph** | `langchain` 1.5.2, `langgraph` 1.2.24 (Python) | Big ecosystem, stateful graphs, LangSmith evals | Layers of abstraction hide the agent loop and the API changes often, which works against a project that proves mechanisms by breaking them. **Leaning no.** |
| **Mastra** | `@mastra/core` 1.85.0 | A full TypeScript agent stack: agents, workflows, memory, RAG, evals | This is the "run it all in the frontend" option: bot logic and tools in TypeScript, memory and evals outside the Python tests. Conflicts with "business rules in Python". **Leaning no.** |
| **Vercel AI SDK** | `ai` 7.0.179, `@ai-sdk/react` 4.0.183 | The best chat UI tooling: `useChat`, streaming, tool calls drawn as UI, tools that run in the browser | **Leaning yes, for the UI only.** It can consume a stream from a Python backend, and browser-side tool calls are how "add to cart" reaches localStorage. |
| **Anthropic / OpenAI SDK** (Python) | `anthropic` 2.12.0 | Thin, every step visible; tool use, structured output, prompt caching | **Leaning yes** before OpenRouter came up (see §4). |
| **OpenRouter SDK** *(owner raised it, to try free models)* | `openrouter` 1.3.203 (Python, beta), `@openrouter/sdk` 1.5.128, `@openrouter/ai-sdk-provider` 3.1.0 | One OpenAI-style gateway to many models, including free ones and Claude | **Current leaning: the gateway** (see §4). |

Also noted, not pursued:
- **Pydantic AI** (2.71.0): a reasonable thin Python option if staying provider-neutral matters.
- **Anthropic Managed Agents:** Anthropic hosts the loop. Every tool here is a local
  database call, so it adds sessions and runtime billing for little gain.

## 4. OpenRouter

**What it offers.** On 21 November 2026 the live model list had 476 models, 14 of them
free. Free models that support tool calling include:

| Model | Context | Tools | Structured output |
|---|---|---|---|
| `google/gemma-4-31b-it:free` | 262K | ✓ | ✓ |
| `google/gemma-4-26b-a4b-it:free` | 262K | ✓ | ✓ |
| `nvidia/nemotron-3-ultra-550b-a55b:free` | 1M | ✓ | ✗ |
| `nvidia/nemotron-3.5-super-vl:free` | 1M | ✓ | ✓ |
| `inclusionai/ling-3.2-flash:free` | 1M | ✓ | ✓ |
| `openrouter/free` (picks a free model per request) | 200K | ✓ | ✓ |

**Catches with free models:**
- **Daily limits.** The help centre lists 20 requests a minute and 50 a day, rising to
  1,000 a day after buying more than $10 of credits. One run of a 100-case eval exceeds
  50, and a single chat turn with tools can use 3–5 requests.
- **Training on prompts.** Each provider sets its own policy, and several free ones
  (NVIDIA among them) may train on prompts. Turning training off in settings can leave
  some free models with no endpoint ("No endpoints found matching your data policy").
  The shop data is invented, but chat logs still go to those providers.
- **The free list changes.** Eval runs must record the exact model ID, and
  `openrouter/free` must never be used for scored runs.
- **Quality varies.** Small models make more malformed or invented tool calls, and some
  have no structured output. The evals become the way to measure this.

**Revised leaning:** OpenRouter as the single gateway, called from Python, with the
model ID as a setting. We write the tool loop ourselves against its chat API, so every
step stays visible. The same harness runs a Gemma, a Nemotron or Claude, and the eval
suite scores them side by side, so comparing models becomes a feature.

The cost is losing some Claude-only features of Anthropic's own SDK, such as strict tool
schemas and native reasoning between tool calls. Add a direct Anthropic connection only
if one is needed.

**Embeddings** come from a local model (fastembed or sentence-transformers), not an API.
That keeps the seed reproducible and costs nothing. Anthropic offers no embeddings;
Voyage AI is the paid alternative.

## 5. Ownership: current leaning

**Python owns the bots; Next.js only shows them.**

```
Browser ── useChat (AI SDK UI) ── applies cart actions to localStorage
   │
Next.js route handler ── proxies the stream, as it does for checkout
   │
FastAPI  commercelab/assistant/   (proposed location)
   ├─ shop bot:  tools = catalogue search, product detail, cart quote   (public data only)
   ├─ admin bot: tools = read-only analytics queries over DuckDB        (may see unit_cost)
   ├─ gateway:   OpenRouter, model ID from settings
   ├─ privacy:   the layers in §6, between every tool and the model
   ├─ retrieval: pgvector in PostgreSQL, local embeddings rebuilt from the seed
   └─ evals:     pytest suites (fixed tool-call checks + an LLM grader)
```

The Next.js side keeps the role the storefront spec already gives it: rendering,
streaming and convenience validation.

## 6. Privacy and security layer

**Goal** *(owner)*: a layer between the LLM API and the data, so that personal data
never reaches a model, for privacy and for security. The owner asked for both the cost
and the expected latency.

### Where personal data could reach a model

1. **Shop bot tool results:** catalogue only, so none, provided its tools never touch
   customer tables.
2. **What shoppers type into the chat:** addresses, emails or phone numbers. Only a text
   filter catches these.
3. **Admin bot query results:** `customers`, `orders` and `order_addresses` hold names,
   emails, phones, addresses and VAT numbers. This is the largest risk.
4. **Stored transcripts, traces and eval sets:** a copy of whatever went to the model.

### Layers

Everything runs locally, so the money cost is £0 per request. The real costs are
latency, memory and build effort.

| Layer | What it does | Added latency | Memory | Build effort |
|---|---|---|---|---|
| **1. Database permissions** | Each bot gets its own read-only PostgreSQL role. The admin bot reads views with no name, email, phone or address columns. Customers appear as a stable pseudonym (`C-0042`); location only as the postcode district (`SW1A`). | ~0 | 0 | Small |
| **2. Pattern rules** | On user text and on anything going out to the model: emails, UK phones, postcodes, card numbers (Luhn check), VAT numbers, IBANs. | under 1 ms | ~0 | Small |
| **3. Reversible placeholders** | The model sees "C-0042"; the server swaps the real name back in after the model's output. Needs a short hold-back while streaming so a placeholder split across chunks still gets replaced. | under 1 ms per chunk | small | Medium |
| **4. Name and address detection** | GLiNER loaded in-process with the `gliner` Python package *(owner)*. A small encoder of about 200–300M parameters, with no separate service and no LLM call. Catches free-text names and addresses that pattern rules miss. | about 10–40 ms per chat message on the M4's CPU, possibly lower on its GPU (estimate) | about 1 GB at full precision, about 300 MB with the ONNX build (estimate) | Medium |
| ~~LLM-based detection~~ | Rejected: an extra model call of 0.5–2 s that sends the personal data to a model to find it | – | – | – |

**For scale:** one bot turn with tools takes about 1–10 s on free models. All four
layers together add roughly 1–3% to that. Layer 4 only needs to run on new user text.

**Owner's correction on GLiNER.** The anonymiser project's run of
`urchade/gliner_multi_pii-v1` peaked near 3 GiB, but that was a bulk ingest of far more
data. Chat messages are short (20–60 words), so that figure does not apply here.

**Where it runs:**
- **Docker on a Mac can't use the M4's GPU.** The backend streams run in Linux
  containers, so GLiNER runs on the CPU there. GPU speed only applies with the backend
  running directly on the Mac.
- **Backend containers are limited to 1 GB.** A full-precision checkpoint would use most
  of that. The ONNX build fits; otherwise raise the limit for the stream that owns the
  assistant. Knowledgator's PII checkpoint ships an ONNX file; the other candidates are
  unconfirmed.
- The anonymiser project's entity-detector bake-off (design dated 19 October 2026) is a
  ready-made way to choose between `urchade/gliner_multi_pii-v1`,
  `knowledgator/gliner-pii-base-v1.0` and `fastino/gliner2-privacy-filter-PII-multi`.

### Security

Stripping personal data does not stop prompt injection. What limits the damage is what
the bots are allowed to do:
- a separate database role per bot
- read-only access
- the admin bot queries approved views only
- row limits and statement timeouts
- no customer-reading tool for the shop bot

A role that cannot read the email column is stronger than any filter. It is the same
"the database enforces it" approach as checkout.

### The leak test

Every seeded customer is invented and known. A test records every outbound LLM request
through a fake provider and fails if any seeded name, email, phone or address appears in
one. Breaking a view on purpose should make it fail (the project's mutation-check
practice).

**Builder's leaning:** build Layers 1–4 and the leak test from the start, now that
Layer 4 is cheap. Layer 3 depends on open question 3.

## 7. Open questions for the owner

1. **What these features are mainly for.** Learning AI engineering (retrieval quality,
   scoring, evals) puts measurable evals first and keeps the bots narrow. Making the shop
   feel real puts the chat UI and the cart hand-off first, with evals as a safety net.
2. **A paid reference model, or everything free?** This matters most for the evals: a
   free model grading another free model gives weak scores. A paid grader such as Claude
   costs a little per run but makes comparisons trustworthy.
3. **Does the admin bot ever name individual customers** ("top 10 customers this
   month")? If yes, Layer 3 is required. If it only reports totals and trends, Layer 1
   covers it.
4. **Shop bot reach** (not yet discussed): does it stop at building the basket, or can it
   start checkout? Starting checkout brings in payments and the idempotency rules.

## 8. Next steps

1. **GLiNER measurement spike** (offered, deferred by the owner). Install `gliner` into a
   temporary environment outside both repos, download one PII checkpoint (about 1 GB),
   time a few hundred chat-sized messages on CPU and on the M4's GPU, and report p50/p95
   latency and memory. Neither repo changes.
2. Answer the open questions in §7.
3. Settle the approaches, then write the spec in `docs/superpowers/specs/` and follow
   the usual pipeline (builder check, plan, contract freeze).
